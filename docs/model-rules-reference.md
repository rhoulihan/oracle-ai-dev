# Model validation & generation rules — the reference

Everything the plugin checks and everything it emits, in one place: the
ModelSpec/QuerySpec contract, the validation mechanisms that gate generation,
the generation rules per physical shape, and — per shape — the split between
**hard-coded rules** (code refuses, warns, or constructs; you cannot drift past
them) and **prompt guidelines** (design judgment the agent applies; you can
override them, and sometimes should).

For tuning knobs and injecting your own standards, see
[tuning-and-custom-standards.md](tuning-and-custom-standards.md) — including the
shipped agent tier of the local-knowledge store (`.oracle-ai-dev/standards.md`
plus the one-time gap-fill), whose *active* directives take precedence over the
defaults in this document, with the carve-out for the non-overridable three:
the destructive-operation override, nothing-identifying-ships, and the claims
guardrails.

## How rules work here

The plugin runs on two tiers. **Deterministic tooling** (`tooling/`) decides
everything a program can decide — schema validity, DDL emission, index
derivation, the measured election, plan checks. **Agent prose** (`skills/`)
carries the judgment a program cannot make — embed vs reference, which
aggregates deserve views, when single-table preconditions hold. The repo's
standing rule (CONTRIBUTING.md, enforced by `tests/test_rule_provenance.py`)
keeps the boundary honest: any reference written in RULE/CHECK form must cite
the code that enforces it or carry an explicit `> Advisory:` marker.

Every rule in this document sits on one rung of the severity ladder:

| Severity | Meaning | Example |
|---|---|---|
| **blocker** | Generation refuses — the artifact cannot exist or would be silently wrong | keyless duality root → `DualityGateError` |
| **warning** | Generation proceeds and annotates the output | `-- WARN [gate-12]:` above a writable view |
| **by construction** | The generator cannot emit the wrong form at all | `_id` is always the first projected field |
| **tripwire** | A test fails the build if any surface starts emitting the banned form | an index targeting a `*_dv` view |
| **live check** | Needs the running database's dictionary; run the published CHECK there | nullability of composite `_id` columns |
| **advisory** | Judgment; the agent applies it and you may override it | one projection per consumer contract |

## The ModelSpec

The single JSON contract every generator and the optimizer consume
(validated by `validate_model` in `tooling/generate/model.py`):

```json
{
  "entities": {
    "Order": {
      "table": "orders",
      "pk": "order_id",
      "columns": {"total": "total", "orderedAt": "ordered_at"},
      "column_types": {"total": "NUMBER(10,2)"},
      "arrays": ["tags"]
    }
  },
  "relationships": [
    {"from": "Order", "to": "OrderItem",
     "from_key": "order_id", "to_key": "order_id", "cardinality": "1:N"}
  ],
  "projections": {
    "duality":      {"Order": [{"view": "order_dv", "includes": ["OrderItem"]}]},
    "document":     {"Order": {"collection": "order_docs", "id_path": "$._id"}},
    "single_table": {"table": "converged_items", "discriminator": "type",
                     "types": {"order": {"key": ["order_id"]}},
                     "indexes": [], "anchor": "order"}
  }
}
```

### Entities

| Key | Required | Meaning |
|---|---|---|
| `table` | yes | base table name |
| `pk` | yes | primary key column — a **string**, or a **list** for a composite key |
| `pk_type` | no | SQL type for a non-identity PK (e.g. `"VARCHAR2(8)"`); default is `NUMBER GENERATED BY DEFAULT AS IDENTITY` |
| `columns` | no | `{property: column}` map — property names are the JSON/document field names, columns the relational names |
| `column_types` | no | `{property: SQL type}` — highest-precedence type source; otherwise FK columns inherit the referenced PK's type, and remaining types are inferred from name tokens (`total`→NUMBER, `ordered_at`→TIMESTAMP, else VARCHAR2(4000)) — `tooling/generate/ddl.py` |
| `arrays` | no | property names whose values are JSON arrays — drives MULTIVALUE indexing and `JSON_EXISTS` predicates (`tooling/generate/model.py`) |
| `partition` | no | the partition dimension — one-line summary in [The storage dimensions](#the-storage-dimensions-per-entity) below |
| `organization` | no | `"heap"` (default) or `"index"` (IOT) — see [The storage dimensions](#the-storage-dimensions-per-entity) |
| `compress` | no | `"advanced"` — Advanced Row Compression — see [The storage dimensions](#the-storage-dimensions-per-entity) |

#### The storage dimensions (per entity)

Three optional per-entity blocks that change *storage*, not SQL. All three
are validated in `tooling/generate/model.py`, emitted by
`tooling/generate/ddl.py` in the clause order the live engine accepts, and
each has a knob that measures the same design without it.

**`partition`** — lifecycle partitioning on this entity's table (the
relational and hybrid lanes; the summary lane inherits it):

```json
"partition": {"by": "interval", "column": "placed_at",
              "interval": "NUMTOYMINTERVAL(1,'MONTH')"}
```

- `by`: `"interval"` (time-series TTL), `"auto_list"` (enumerable
  categories), or `"hash"` (spread).
- `interval` needs an initial boundary: time-typed columns get a far-past
  default; anything else must declare `initial` explicitly.
- Optional: `partitions` (hash count, default 8), `seed_value` (auto_list),
  `local_indexes` (default `true` — the entity's derived B-tree indexes are
  built `LOCAL`).
- Knob: `--no-partition` suppresses every partition block.
- Limits, disclosed: document collections are NOT partitioned by this block
  (the expression-column route is prose, not mechanism); a duality view over
  a partitioned base is doc-unstated but live-proven
  (`tests/test_live_hybrid_partition.py`).

**`organization`** — `"heap"` (default) or `"index"`: index-organized
storage, where the table IS its primary-key B-tree, so a PK-led read stops
at the leaf instead of following a rowid into a second segment.

- Optional overflow tuning: `pctthreshold` (1–50 — the percent of the block
  the in-leaf row piece may use) and `including` (the last column kept in
  the leaf; everything after it moves to overflow).
- The `OVERFLOW` segment is always emitted: name-inferred `VARCHAR2(4000)`
  columns make a >50%-of-block max row the common case, and an IOT without
  one cannot even be created (live-isolated ORA-01429).
- Emitted clause order (live-verified):
  `ORGANIZATION INDEX [PCTTHRESHOLD n] [INCLUDING col] OVERFLOW`.
- Three engine-enforced conflicts are **blockers**, refused at validation
  time naming the ORA they prevent:
  - with `compress` → ORA-00922;
  - with a `partition` family other than `hash` → ORA-25198 (and the hash
    key must be a primary-key column — ORA-25199);
  - with hybrid flex properties on the same entity → ORA-61714 (no
    MULTIVALUE index on an IOT, so flex predicates would silently
    full-scan).
- A duality view over an IOT base is doc-unstated but live-proven
  (`tests/test_live_iot_compress.py`).
- Knob: `--no-iot` measures the same design as a heap.

**`compress`** — `"advanced"`: Advanced Row Compression on this entity's
base table (included on Free).

- `"basic"` is rejected, with the measured reason: BASIC compresses only
  direct-path loads and updates decompress the block — a conventionally
  written table would measure a design that does not exist in production.
- Emits `ROW STORE COMPRESS ADVANCED` after the column list, before any
  partition clause; composes with the partition dimension; refused on an
  `organization: "index"` entity (ORA-00922).
- Knob: `--no-compress` — the counterfactual the write cells' elapsed/redo
  diagnostics are read against. Live-asserted in
  `tests/test_live_iot_compress.py`.

### Relationships

| Key | Required | Meaning |
|---|---|---|
| `from`, `to` | yes | entity names (must exist) |
| `from_key`, `to_key` | yes | the join columns on each side — **directed column pairs; never assumed to share a name** |
| `cardinality` | no | `1:N` (default), `N:1`, or `1:1` |

### Projections

- **`duality`** — `{root: decl}` where `decl` is a bare **string** (one all-in
  view over every reachable entity), a **dict**, or a **list of dicts**
  `{"view", "includes", "columns"}`. `includes` scopes which entities nest;
  `columns` (`{entity: [props]}`) scopes the payload. One view per aggregate is
  the intended form — a view costs exactly what it nests.
- **`document`** — `{root: {"collection", "id_path"}}`; `id_path` defaults to
  `"$._id"`.
- **`hybrid`** — `{"entities": {name: {"flex": [props]}}}`. Each listed
  property moves from a typed column into that entity's `flex JSON (OBJECT)`
  column on the hybrid lane's own `<table>_h` tables. Flex may not take the
  primary key or a relationship key (validated). When absent, the optimizer
  nominates a hybrid candidate by heuristic: properties no pattern filters,
  groups, aggregates, orders on or writes go to flex; everything
  access-path-anchored stays a typed column.
- **`single_table`** — `{"table", "discriminator"` (default `type`)`,
  "types": {name: {"key": [cols]}}, "indexes": [{"name","type","columns",
  "sparse"}], "anchor"}`. `anchor` names the type whose key becomes the
  deliberately non-sparse anchor index (the item-collection read).
  `model_from_dynamodb` in `tooling/generate/ingest.py` produces this whole
  projection from a NoSQL Workbench export.
- **`summary`** — `{"mvs": [{"name", "query": {root, group_by, aggregates}}]}`.
  Each entry declares one materialized aggregate: a **single-root aggregation
  query** over that root's `_s` table (names unique; the query must be an
  aggregation and its entities must exist — multi-entity join MVs are not
  emitted). When absent, the optimizer auto-nominates one MV per distinct
  aggregation signature (root + group-by set + aggregate list) among the
  workload's read patterns, so the shape competes by default; a workload with
  no aggregation patterns nominates none and the candidate does not appear.

## The QuerySpec and the workload

Each access pattern's query (validated by `validate_query` in
`tooling/generate/model.py`):

| Key | Meaning |
|---|---|
| `root` | the entity the pattern starts from (required) |
| `returns` | `["Entity.prop", ...]` (required unless `group_by` present) |
| `predicates` | `[{"ref", "op", "value"}]`; ops `=`, `!=`, `<`, `<=`, `>`, `>=`, `IN`, `BETWEEN`, `IS [NOT] NULL` |
| `group_by`, `aggregates` | aggregation — `aggregates: [{"name", "fn", "ref"}]` |
| `order_by`, `limit` | `[{"ref", "dir"}]`, integer |
| `computed` | derived expressions (routes duality → SQL view) |
| `requires_ops` | operations the projection must express; any of `coalesce, decode, case, derived, computed, group_by, aggregate, window, distinct, union` routes the query OFF duality (`DUALITY_UNSUPPORTED`, `tooling/generate/model.py`) |
| `attribute_kv` | marks an attribute-list/KV realization: predicates treated as array containment |
| `type` / `types` | single-table discriminator value(s) the pattern touches |

Workload patterns (the optimizer's input, `tooling/optimize/__main__.py`) wrap
a query with `{"name", "kind": "read"|"write", "rate", "category", "query",
"write": {...}, "expect_rows"?}`; `expect_rows` declares the magnitude the
pattern should answer — a deciding cell under it is flagged `!! PROVISIONAL`
(`tooling/optimize/runner.py`). The same decision block discloses `decided by:` —
a verdict won on point reads carries to Exadata-class deployments (buffer-cache
point reads never offload), while one won on scan economics is announced as
environment-conditional and must be re-validated on the target, since smart scan
and storage indexes cheapen exactly that access path. The spec also takes
`seed` (inline SQL, `.sql` path, or a
list) and `scenarios` (named rate re-weightings). The intake layer that
produces requirements upstream of a model has its own schema-validated
contract: `tooling/intake/schema.json` + `tooling/intake/validate.py`
(workload class, entities, access patterns with frequencies, required
features, deployment target).

## Cross-shape validation mechanisms

These run regardless of shape:

1. **Spec validation** — `validate_model` / `validate_query`
   (`tooling/generate/model.py`): entities need `table` + `pk`, relationships
   need known entities and both keys, every `Entity.prop` reference must
   resolve. Generation never runs on an invalid spec.
2. **Duality expressibility routing** — `duality_supports` sends any query
   whose `requires_ops` intersects `DUALITY_UNSUPPORTED` to the read-only SQL
   view instead. A duality view must stay updatable; it cannot GROUP BY.
3. **The optimizer's invariants** (`tooling/optimize/runner.py`):
   - **Answer equivalence before timing** — every design must return the same
     answer, compared shape-independently (`tooling/optimize/equivalence.py`,
     `tooling/optimize/compare.py`); a design that answers differently is
     disqualified and reported, never silently timed.
   - **The noise gate** — `NOISE_FLOOR = 0.05` is a floor, not the gate: the
     effective floor rises to the worst per-cell coefficient of variation among
     the cells the verdict rests on. Inside the floor the verdict is reported
     as too close to call, not decided.
   - **A missing cell means EXCLUDED, not penalized** — a design that cannot
     serve a pattern is not viable; it is not handicapped and kept.
   - **The safety guard** (`tooling/optimize/safety.py`) — destructive
     operations (`--fresh` drops) are refused on any non-local DSN unless
     `OPT_ALLOW_EXTERNAL_WRITES=1`.
4. **Duality design gates** — `tooling/duality/validate.py`, run at the DDL
   emit choke point and standalone via `python -m tooling.duality
   <model.json>` (exit 1 on blockers). Detailed in the duality matrix below.
5. **Plan checking** — `python -m tooling.plancheck "SELECT ..."` pulls the
   plan through the same EXPLAIN path the optimizer uses
   (`tooling/plancheck/check.py`) and exits 1 when a filtered query
   full-scans.
6. **Tripwires** — the build fails if any generated or shipped surface emits a
   non-GA locality clause (`tests/test_set_locality_blocklist.py`), an index
   targeting a duality view, or a VPD policy on a view
   (`tests/test_duality_ddl_blocklist.py`).
7. **Content lints** — banned-terminology and do-not-cite scans plus the
   maintainer-local confidential register (`tests/lint/banned_strings.py`);
   the ETag write-path contract is proven live by
   `tests/test_write_conflict_live.py`.

## The matrix — hard-coded rules vs prompt guidelines, per shape

The generator serves seven shapes: `relational`, `document`, `hybrid`,
`duality`, `summary`, `single_table`, and `sql_view`. For each: first what the
code enforces, then the judgment the skills supply. Guideline tables are advisory
by definition — sources are the skill references the agent loads.

### relational — normalized tables

**Hard-coded** (`tooling/generate/ddl.py` unless noted):

| Rule | Action | Where |
|---|---|---|
| Single-column PK defaults to `NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`; `pk_type` overrides | by construction | `tooling/generate/ddl.py` |
| Composite PK emits typed key columns + a named table-level constraint | by construction | `tooling/generate/ddl.py` |
| FK columns are typed FROM the referenced PK's type — a VARCHAR2 key never gets a NUMBER FK | by construction | `tooling/generate/ddl.py` |
| Column types: `column_types` > FK-matched type > whole-token name inference (substring matching produced `country`→`count` false positives; tokens only) | by construction | `tooling/generate/ddl.py` |
| One composite index per (entity × query) over that query's predicate columns; PK columns skipped (already indexed); `IS [NOT] NULL` never indexed | by construction | `generate_indexes`, `tooling/generate/ddl.py` |
| Aggregations imply indexes too — GROUP BY keys + aggregate arguments, named for their columns so same-entity aggregations cannot collide (ORA-00955 swallowed as "exists" left relational with no indexes at all, once) | by construction | `tooling/generate/ddl.py` |
| Generated queries bind every input by name; no literal is ever inlined | by construction | `tooling/datalayer/generate.py` |

**Prompt guidelines** (advisory):

| Guideline | Source |
|---|---|
| Reference unbounded/shared/independent children; normalize along change-rate seams | `skills/oracle-data-modeling/references/decision-rules.md` |
| Do not decompose arrays of subdocuments into child tables out of relational habit — measured 9–15× against; join/aggregate-heavy families still go relational | `skills/oracle-data-modeling/references/field-lessons.md` |
| Constrain the canonical, not the consumer — CHECKs/FKs on base tables so every projection inherits them | `skills/oracle-data-modeling/references/decision-rules.md` |
| Composite index column order: Equality, then Sort, then Range | `skills/oracle-data-modeling/references/decision-rules.md` |

### document — JSON collection table

**Hard-coded:**

| Rule | Action | Where |
|---|---|---|
| A document projection requires a declared `collection`; generation refuses without it | blocker (ValueError) | `tooling/generate/ddl.py` |
| **Dot notation first**: scalar predicates render as plain dot (`d.data.prop = :b`) — the only form measured to match the shared multivalue index regardless of which lane created it; an item method ON a predicate (`.string() =`) is never emitted (it loses the match) | by construction | `tooling/generate/sql.py`, `tooling/datalayer/generate.py`, guarded by `tests/test_dot_notation_first.py` |
| Scalar predicate fields get typed-item-method **MULTIVALUE** indexes (`.numberOnly()` / `.string()`), **one per field, deduplicated by (collection, field)** — a composite multivalue over scalars is invalid SQL (ORA-44981), and per-field is exactly the form a Mongo `createIndex` produces, so one index serves both lanes; scalar `JSON_VALUE` functional indexes are never emitted (the Mongo lane can't use them) | by construction | `tooling/generate/ddl.py` (`dot_typed_expr`) |
| Aggregation and ORDER BY expressions use the typed item methods — the type is preserved without `RETURNING`, and the derived index carries the identical expression | by construction | `tooling/generate/ddl.py` (`agg_expr`), `tooling/generate/sql.py` |
| The `_id` point-read keeps the typed `JSON_VALUE` + its functional index — the documented LAST RESORT (scalar ids, live-measured; the shared-lane `_id` evidence is ObjectId-specific) | by construction | `tooling/generate/ddl.py` (`json_value_expr`) |
| Declared `arrays` properties get MULTIVALUE indexes and `JSON_EXISTS` containment predicates — containment is a different question from equality, and `JSON_VALUE` of an array matches nothing | by construction | `tooling/generate/ddl.py`, `tooling/generate/model.py` |
| Generated document writes are whole-document `JSON_TRANSFORM` updates | by construction | `tooling/generate/sql.py` |

**Prompt guidelines** (advisory):

| Guideline | Source |
|---|---|
| Embed bounded/owned/co-accessed children; document shape is a first-class realization, not a fallback | `skills/oracle-data-modeling/references/patterns.md`, `decision-rules.md` |
| Size the aggregate at typical AND P99 against the OSON inline threshold (~7,950 bytes; past it the document falls to LOB storage — a cliff) | `skills/oracle-data-modeling/references/review-checklist.md` |
| Multivalue index cost ≈ array cardinality × mutation rate; churning arrays tip toward referenced documents | `skills/oracle-data-modeling/references/decision-rules.md` |
| Shared collections (Mongo API + SQL): write numerics with an explicit type — the JS bare-number default (BSON double) breaks the SQL lane's strict dot matching; answers stay correct, the access path degrades | `skills/oracle-data-modeling/references/optimization.md`, `skills/mongodb-api-dev/references/connect.md` |
| Index known hot paths with multivalue indexes; a search index only for genuinely ad-hoc query surfaces, created `SYNC (ON COMMIT)` | `skills/sql-json-dev/references/json-indexing.md` |
| Sort and limit raw columns; construct JSON only for the survivors | `skills/oracle-data-modeling/references/field-lessons.md` |
| Every collection gets a growth bound or an explicit "unbounded by design"; purge with `deleteMany`, never `drop()` | `skills/oracle-data-modeling/references/field-lessons.md` |

### hybrid — relational core + JSON flex column

The Phase-1 shape: typed columns for the stable, access-path-anchored
properties; one `flex JSON (OBJECT)` column per entity for the variable/sparse
rest — on the lane's own `<table>_h` tables, so the flex column can never
perturb the relational design's row width mid-measurement.

**Hard-coded** (`tooling/generate/ddl.py` unless noted):

| Rule | Action | Where |
|---|---|---|
| A hybrid projection requires per-entity `flex` lists; flex may not take the PK or a relationship key, and every flex name must be a declared property | blocker (validation) | `tooling/generate/model.py` |
| The flex column is emitted with `JSON (OBJECT LIMIT 8192)` — the inline guarantee that makes the OSON inline-to-LOB decay cliff impossible by construction (an oversize insert is rejected with ORA-42712, live-verified; the LIMIT belongs INSIDE the type-constraint parens — outside raises ORA-03099); the limit is a knob (`flex_limit`) | by construction | `tooling/generate/ddl.py` |
| Core predicates render as plain column conditions; flex scalar predicates as plain dot on the flex column (`alias.flex.prop = :b`) — the document lane's dot-notation-first doctrine, applied to flex | by construction | `tooling/generate/sql.py`, guarded by `tests/test_hybrid_shape.py` |
| Flex predicate fields get per-field typed-item-method MULTIVALUE indexes on the `_h` table; core predicate fields get composite B-trees — mixed derivation through the same shared helpers | by construction | `tooling/generate/ddl.py` |
| Flex arrays are `JSON_EXISTS` containment + a MULTIVALUE index over the elements, exactly as in the document lane | by construction | `tooling/generate/sql.py`, `tooling/generate/ddl.py` |
| Aggregation/ORDER BY on flex uses typed item methods; on core, the plain columns — query and index sides share one expression helper | by construction | `tooling/generate/ddl.py` (`agg_expr`) |
| Core writes are single-row column updates; flex writes are `JSON_TRANSFORM` on the flex column only (not a whole-document rewrite) | by construction | `tooling/generate/sql.py` |
| The hybrid lane is DERIVED from the relational seed (INSERT..SELECT with `JSON_OBJECT ... ABSENT ON NULL`), parents-first — identical rows, sparse attributes stay absent | by construction | `tooling/optimize/runner.py` (`hybrid_populate_sql`) |
| When no hybrid projection is declared, the optimizer nominates one by heuristic (unanchored properties → flex) so the shape competes by default | by construction | `tooling/optimize/runner.py` (`propose_hybrid`) |

**Prompt guidelines** (advisory):

| Guideline | Source |
|---|---|
| Nominate hybrid for stable join/filter/aggregate keys + open-ended per-instance attributes — typed columns for what patterns anchor on, ONE JSON column for the rest | `skills/oracle-data-modeling/references/decision-rules.md` |
| Never a nullable column per variant metric; never a flex property that patterns filter or aggregate at high rate — move it to a typed column instead | `skills/oracle-data-modeling/references/decision-rules.md` |

### duality — JSON-relational duality view

The most heavily gated shape. The 24 design gates
(`skills/oracle-data-modeling/references/duality-design-gates.md`) map to
mechanism as follows — the spec-decidable subset is enforced at the single
emit choke point (`generate_ddl(model, "duality")` raises
`DualityGateError`) and reviewable standalone with
`python -m tooling.duality <model.json> [--root R]`:

| Gates | Rule | Action | Where |
|---|---|---|---|
| 1 | A keyless table cannot root a view (the root key becomes `_id`) | **blocker** | `tooling/duality/validate.py` |
| 2 | Every included entity must exist and be reachable from the root (parent, child, or junction far-side) — the generator would otherwise silently omit it | **blocker** | `tooling/duality/validate.py` |
| 3 | Every nesting join's parent side must be that entity's key — a non-unique join fans rows out and breaks one-document-per-root | **blocker** | `tooling/duality/validate.py` |
| 9 | Every declared column type must sit on the duality allowlist | **blocker** | `tooling/duality/validate.py` |
| 11 | No duplicate JSON keys at one object level; no self-nesting (the spec has no distinct-predicate syntax) | **blocker** | `tooling/duality/validate.py` |
| 12 | Generated views are writable by default (the optimizer must measure writes); record each writable table deliberately | **warning** (`-- WARN [gate-12]`) | `tooling/generate/ddl.py` |
| 18 | A single all-in view over a multi-entity aggregate makes every point read pay the widest read's joins | **warning** (`-- WARN [gate-18]`) | `tooling/generate/ddl.py` |
| 5, 7, 13, 14 | Cardinality decides object vs array; `_id` first; junction arrays keep `@delete`; a junction's far side ships as a named nested object carrying its payload (an `@unnest` block omitting the far PK kills the session — ORA-00600) | by construction | `tooling/generate/ddl.py` |
| 16 | The write path round-trips `_metadata.etag`: the generated `replace_<root>_doc` refuses a stripped `_metadata` and maps ORA-42699 to `StaleDocumentError` | mechanism | `tooling/datalayer/platforms.py`, proven live by `tests/test_write_conflict_live.py` |
| 22, 23 | No VPD on a view; no index on a view — base tables only | tripwire | `tests/test_duality_ddl_blocklist.py` |
| 4, 6, 8, 10, 15, 17, 19–21, 24 | Directed join pairs in the dictionary, embed options, `_id` supplier, textual JSON, ETag scope, projection taxonomy/minimum fields/no-view entities, migration layering | live check / advisory | run the CHECK blocks in the gates file against the target |

**Prompt guidelines** (advisory):

| Guideline | Source |
|---|---|
| Duality views are read-time joins: costlier reads for zero write amplification — never serve a write-hot path through one | `skills/json-duality-dev/references/duality-design.md` |
| Array children project their FULL primary key (a composite-PK array child missing a key column throws ORA-40477 on read) | `skills/json-duality-dev/references/duality-design.md` |
| Annotate mutability per table (`@noinsert @update @nodelete` for lookups); creation is SQL-only | `skills/json-duality-dev/references/duality-design.md` |
| Re-root, never overload: another consumer needs another view, not a wider one | `skills/oracle-data-modeling/references/duality-design-gates.md` |
| Projection scope IS authorization: minimum fields per consumer contract; secrets ride only trusted-path views; some entities deliberately get no view | `skills/oracle-data-modeling/references/duality-design-gates.md` |

### summary — materialized aggregates over a relational core

The relational core on the lane's own `<table>_s` tables, plus the declared
materialized aggregates over it. A read whose aggregation matches a declared
MV reads the MV directly; everything else — point reads, filtered reads,
non-matching aggregations, writes — is ordinary relational SQL on the `_s`
lane, so the design answers the whole workload. Every write pays the MV's
incremental maintenance, which makes the precompute inequality a *measured*
quantity instead of a prose gate.

**Hard-coded** (`tooling/generate/ddl.py` unless noted):

| Rule | Action | Where |
|---|---|---|
| MVs are emitted `REFRESH FAST ON COMMIT` — the probe decided the mode, not preference: an aggregate `REFRESH FAST ON STATEMENT` MV is refused by the engine (ORA-32428, "shape of MV is not supported"; live-verified on 26ai Free 23.26.2), so the statement-fresh route does not exist for aggregates | by construction | `tooling/generate/ddl.py`, `tests/test_summary_design.py` |
| One materialized view log per base `_s` table — `WITH ROWID, SEQUENCE (<cols>) INCLUDING NEW VALUES` — with the column set MERGED across every MV rooted on that table; a log short one referenced column silently disqualifies fast refresh | by construction | `tooling/generate/ddl.py` |
| COUNT companions are appended to every MV's select list (`COUNT(*)`, plus `COUNT(<arg>)` per SUM/AVG): the documented fast-refresh eligibility requirement for aggregate MVs | by construction | `tooling/generate/ddl.py` |
| MVs and their logs deploy with `IF NOT EXISTS`, and a duplicate create (ORA-12006) is tolerated as "already exists" — deploys are idempotent, both live-verified | by construction | `tooling/generate/ddl.py`, `tooling/optimize/runner.py` |
| A read whose root, GROUP BY set and aggregate subset MATCH a declared MV is generated as `SELECT … FROM <mv_name>` — a deterministic direct read (QUERY REWRITE is prose, not mechanism); residual predicates must sit on group-by references, or the pattern falls back to relational SQL on the `_s` lane rather than reading a summary that cannot answer it | by construction | `tooling/generate/sql.py` |
| Write cells for this shape use the commit-inclusive protocol: `execute + COMMIT` is timed (maintenance is included by physics), the compensating statement + commit runs OUTSIDE the timed region, and the net effect is zero. Other designs' write cells are rolled back, so the bias runs AGAINST summary — disclosed in the report, never synthetically corrected | by construction | `tooling/optimize/runner.py`, `tests/test_summary_design.py` |
| The summary lane owns its storage: `<table>_s` copies plus the MVs and logs. An MV over the SHARED base tables would charge its maintenance to the plain relational design's write cells — the measurement would tax a design that declared nothing | by construction | `tooling/generate/ddl.py`, `tooling/optimize/runner.py` |

**Prompt guidelines** (advisory):

| Guideline | Source |
|---|---|
| Keep a precomputed subset only if read-freq × read-cost > write-freq × maintenance-cost — nominate `summary` when that inequality is plausible and let the matrix price both sides instead of asserting them | `skills/oracle-data-modeling/references/decision-rules.md` |
| Size a per-key summary against PRODUCTION cardinality before building it: its row count is the sum of each key's reachable set through every mapping on the path, and a mapping that arrives 200× larger than assumed takes the summary from tens of millions of rows to billions | `skills/oracle-data-modeling/references/field-lessons.md` |

### single_table — converged item collection

**Hard-coded** (`tooling/generate/ddl.py` unless noted):

| Rule | Action | Where |
|---|---|---|
| One shared table, a `type` discriminator, the UNION of the types' columns natively typed (no concatenated string keys) | by construction | `tooling/generate/ddl.py` |
| The anchor index is deliberately NOT sparse and NOT local — an item-collection read spans several types, and a type-filtered index cannot serve it | by construction | `tooling/generate/ddl.py` |
| Per-type composite-key indexes are sparse (`CASE WHEN type='t' THEN col END`); a cross-type index must not be LOCAL to a type | by construction | `tooling/generate/ddl.py` |
| Sparsity is part of an index's identity: the same columns may need BOTH a sparse and a non-sparse variant; deduping on columns alone drops one and its read full-scans | by construction | `tooling/generate/ddl.py` |
| Automatic list partitioning by the discriminator (`--no-partition-by-type` and `--no-sparse` disable; the emitted winner is always built exactly as the measured one was) | by construction, tunable | `tooling/generate/ddl.py`, `tooling/optimize/__main__.py` |
| DynamoDB imports decompose concatenated PK/SK into typed columns; Oracle reserved words are renamed safely; each GSI becomes a multi-column index | by construction | `tooling/generate/ingest.py` |

**Prompt guidelines** (advisory):

| Guideline | Source |
|---|---|
| Preconditions: enumerable, priority-ranked, read-heavy patterns over owned data — a tool, not a religion; failing preconditions route to normalized base + duality | `skills/oracle-data-modeling/references/optimization.md` |
| Never replicate GSI index-overloading on Oracle — an overloaded index is maintained by every type it covers and reintroduces generic keys | `skills/oracle-data-modeling/references/optimization.md` |
| The discriminator is load-bearing: set consistently on every write | `skills/oracle-data-modeling/references/review-checklist.md` |

### sql_view — read-only JSON over relational

**Hard-coded:**

| Rule | Action | Where |

### Choosing among the shapes

Selection is **reason, then measure** — deliberately not a rule table:

- A deterministic starting point exists in code:
  `tooling/recommend/shapes.py` encodes UMT's precedence (write-hot →
  single collection; multi-entity read-mostly → duality; bounded/owned →
  embed; single-entity JSON collection as the default). It is reproducible
  and unit-tested — and the skills state it **never overrides reasoning plus
  measurement**.
- The candidates come from the agent's reasoning
  (`skills/oracle-data-modeling/references/decision-rules.md` — an
  escalation ladder, not a menu); the winner comes from the measured
  election (`tooling/optimize/decide.py`): rate-weighted read+write cost,
  noise-gated, with break-points showing where the choice flips.
- The shape choice is a refactor, not a one-way door
  (`skills/oracle-data-modeling/references/umt-methodology.md`).

The division of labor is the design: imagination is the LLM's job; the
numbers are the tooling's.
